01 / The intended design

The feature defines the task. The dataset supplies the answer key.

Bedrock feature

Documented behaviour, input/output side and supported configuration.

Example: membership in a configured denied topic.

→

Shared test contract

One precise task, equivalent information, independently established expected answers.

Bedrock is a competitor, not the answer key.

→

Eligible dataset

Choose examples whose labels match that task. Keep sources and adaptations traceable.

A convenient label must not change the task.

Bedrock implementation

Native feature + declared tier/settings + frozen configuration.

Decision-model implementation

Model + questions + aggregation rule + frozen threshold.

↓ Same eligible test cases and reference answers ↓
Quality · cost · latency, per tested function
Then a declared weighted score across those tested tasks—not a claim of complete product replacement.
02 / The point where we drifted

Better provenance can still describe a different task.

Profanity

Profane-word detection ≠ broader obscenity

Bedrock’s managed profanity feature
≠
Civil Comments’ combined profanity/obscenity label

Original crowd labels improve provenance. They do not make the broader task identical to profanity detection.

Decision: retain obscenity as an auxiliary evaluation.

The prepared v1.3 obscenity work follows an earlier recommendation. Keep any collected results; do not silently substitute them into the native profanity score.

Denied topics

The configured definition is the boundary.

Our investment topic broadly covers inquiries about allocating funds to achieve financial objectives. Some annotation rationales use the narrower idea of personal investment advice.

A general investment question could be labelled differently under those two boundaries.

Decision: review against the exact frozen text.

This is a potential mismatch, not proof that every disputed example is wrong. Human review cannot silently rewrite the topic.

Even human-reviewed profanity labels cannot reveal AWS’s undisclosed vocabulary. The defensible claim is performance against a declared external reference, not exact agreement with AWS’s private list.

04 / What belongs in every feature contract

One record connects the feature to its evidence.

These records should become the current source of truth. Several suite READMEs still describe old smoke tests and the previous PII source.

Every contract records: intended behaviour → shared inputs → each system’s configuration → reference-label rule → transformations and provenance → coverage status.

Preserve the run. Correct the evidence. Version the result.

Create a new evaluation

06 / What the two reviewers disagreed about

The practical position

Keep the completed comparison available with explicit limits. Repair specific tasks without waiting for every Bedrock capability.

The sceptical position

The combined score must not imply feature parity while source labels and task boundaries differ. Correct the mappings before making that stronger claim.

Our decision: retain the scoped results and make a separately versioned correction.
More data comes after task validity. No full restart is required.
Work status: this is an assessment and repair plan. It does not certify the labels, perform the human reviews, change the frozen scores or establish full Bedrock parity.
