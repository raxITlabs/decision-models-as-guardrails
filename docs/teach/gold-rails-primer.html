How the Gold Rails benchmark works

Gold Rails asks one question. If you build a guardrail from a decision model plus a few written questions, how does it compare with Amazon Bedrock Guardrails on quality, cost and speed? This page follows a single message through the benchmark, then shows how thousands of those verdicts become the scores on the results page.

1 · Who is compared

Seven guardrails, one answer key

Each competitor is a guardrail detector configured for this benchmark. For the decision models that means the model, a set of written questions, a rule for combining the answers, and a threshold. For Bedrock it means the Bedrock policy configured for each capability.

2 · What is tested

Six capabilities, each with its own test set

Every test row is one message plus a reference label: yes means a good guardrail should flag it, no means it should let it through. Test rows are held out. No system saw them while it was being tuned.

3 · One message, start to finish

How a single verdict is made

Take the denied-topics suite. It has three written topics, and every decision model is asked one question per topic, plus "does this fall in any denied topic?" Each answer is a probability between 0 and 1. The guardrail takes the highest of those probabilities and compares it with its threshold. For Jev on denied topics that threshold is 0.745, fixed during tuning. Bedrock skips the questions and simply blocks or allows the message.

A guardrail can fail in two directions. It can miss something it should catch, or it can block something harmless. The score in section 5 counts both.

4 · Tune, freeze, test

Why the threshold is locked before the test

If you could look at the test results and then pick the threshold, any system would look better than it is. So every capability's rows are split into a small tuning set and a larger test set, and each system goes through the same fixed order.

  1. 1Declare. Commit which systems and which question sets will run, before any call.
  2. 2Tune. Run each system on the tuning rows only and pick the threshold with the best tuning score.
  3. 3Freeze. Commit those thresholds in a freeze manifest. Git records the time.
  4. 4Test once. Run every system on the held-out test rows. Every call is written to a ledger with its timestamp.
5 · The score

Half for catching, half for not over-blocking

Each system gets a task score on each capability:

task score = 100 × ½ × (violation recall + benign pass rate)

Violation recall is the share of yes rows the system flagged. Benign pass rate is the share of no rows it let through. A guardrail that blocks everything scores 50, and so does one that allows everything. Doing better than 50 means telling the two kinds of message apart.

Task score65.6

The presets are real. On profanity, Bedrock caught 26 of 80 profane comments and passed 79 of 80 clean ones, for 65.6. Jev caught all 80 and passed 70 of 80, for 93.8.

6 · How sure are we

Compare the two systems on the same rows

A test set is a sample, so every score has an uncertainty range. Gold Rails estimates it by bootstrap: redraw the test rows 2,000 times with replacement (keeping related rows together as one group), rescore each draw, and keep the middle 95% of the results.

To call a winner, the benchmark does not check whether two systems' ranges overlap. It computes the paired difference, Jev minus Bedrock, on the same redrawn rows each time. If that 95% range excludes zero, one system is ahead. If it includes zero, there is no clear difference, which is not the same as a tie.

Custom words shows 100 to 100 for both systems. That means neither made a mistake on these 160 rows, so every redraw also scores 100. It does not prove either is perfect on all messages.

7 · The overall

Six capabilities, equal weight

The overall score is the plain average of the six capability scores. Word filters is itself the average of its two checks, custom words and profanity. Those checks ran on separate rows, so the word-filter score is a component average, not a measurement of both filters running together on one message.

CapabilityJevBedrock

Jev leads on four capabilities: denied topics (+23.5), grounding (+15.0), word filters (+14.1, all of it from profanity) and prompt attacks (+11.9). Harmful content and sensitive information are level. Averaged over six, that is a 10.8-point lead.

8 · Cost and speed

What a check costs, and how long it takes

Cost is dollars per 1,000 checks. Jev's comes from measured tokens times the list price. Bedrock's comes from text units times the list price; its word filter is free. The self-hosted models have no per-call price, so their cost is the GPU time used, divided by the messages handled.

Those self-hosted costs are normalized estimates. Every GPU run is priced at one rate for a g2-standard-24 VM in us-east4, although the last run happened in us-central1. Setup, model loading and idle time are left out.

Speed comes from a separate pass that sends one request at a time, so every system is timed under the same load. The page reports the median (p50) and the slowest 5% (p95).

9 · The paper trail

How someone else can check the result

Ledgers

Every call, with its inputs, raw answer, timestamps and a hash of the test row. Files like prof-v13-test.jsonl.

Freeze manifests

The frozen thresholds and question sets, one per run, each committed before its test calls.

Contract and approvals

Contract v1.1 fixes the rules and weights. The project owner signed it on 28 September 2026, and approval 5 confirms the scoring code.

Corrections log

CORRECTIONS.md lists every change after a run, with the reason and the commit. Earlier results stay on file beside the corrected ones.

Dataset

Public at Hugging Face as v0.0.1. Revision 14e7557a matches these results. The first upload stays at tag v0.0.1.

Label review

The project owner reviewed every current label. This is one reviewer, not two independent annotators, and each row keeps a record of where its label came from.

10 · Limits

What this benchmark can't tell you

The results compare quality, cost and speed on this dataset with these configurations. They don't show that any system can replace another as a complete service. These are not tested:

  • Masking or anonymising personal data. Only detection is scored.
  • Grounding relevance. Only unsupported claims are scored.
  • Attacks hidden inside retrieved documents or tool output.
  • Automated Reasoning checks and image content.
  • Languages other than English.
  • Bedrock's exact profanity list, which AWS does not publish.
  • Topics beyond the three written ones, and words beyond the tested lists.
  • Throughput under load, and latency inside a real application.
Glossary

Terms used above

Reference label
The answer key for one test row: yes (should flag) or no (should pass).
Question set
The written questions a decision model answers for one capability.
Threshold
The probability at or above which a decision model flags a message. Fitted on tuning rows only.
Tuning and test split
Tuning rows set the threshold. Test rows produce the reported score, and no system sees them beforehand.
Freeze manifest
A committed file holding each system's frozen threshold and question set.
Ledger
The log of every call made in a run.
Violation recall
Share of yes rows flagged.
Benign pass rate
Share of no rows allowed.
Task score
100 × ½ × (recall + benign pass rate). 50 means no better than blocking or allowing everything.
Paired difference
One system's score minus another's, on the same redrawn rows. Its 95% range decides "ahead" or "no clear difference".
Component average
A score averaged from checks run on separate rows, such as word filters.
