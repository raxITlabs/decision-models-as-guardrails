Gold Rails: where we are

A guardrail benchmark that asks whether decision models such as Jev can stand in for managed guardrails such as Amazon Bedrock Guardrails.

Status as of 23 Sep 2026, morning Work since 21 Sep 16:03 Commits 84 Tests 46 passing

TL;DR

  • We started with an idea for a Jev-powered guardrail API and ended up building the thing that has to come first: an open, reproducible benchmark comparing decision models with Bedrock Guardrails.
  • All six Bedrock capabilities we compare against now have a working smoke suite, run on seven systems: Jev, Kev 0.8B, 4B and 9B, Open-Jev 2B, Laya, and Bedrock itself.
  • On small tuning samples Jev ranks well on attacks, PII, topics and grounding, and over-flags benign scary-sounding text on content. None of that is a result yet.
  • Three outside reviews caught overclaims, a leaky dataset split, mismatched tasks and a scoring bug. All are fixed and written up, and the evaluation rules are tighter for it.
  • All GCP infrastructure is torn down and nothing bills. The four AWS guardrails remain; they cost nothing at rest.
  • Next: review the authored test cases, add the missing coverage, freeze the evaluation contract, then run the held-out comparison.

The goal

Across Bedrock Guardrails' capabilities, how competitive are decision-model implementations on quality, cost and latency, and with what limitations?

The comparison is between complete implementations: a decision model with its questions and decision rule, against a managed service with its supported configuration. Both see the same test cases, and each dataset's own task definition decides what is correct. Automated Reasoning is excluded because formal verification is a different capability. The dataset will be published on Hugging Face under raxITLabs and the results on raxit.ai.

What the reviews changed

Say only what the data shows

Early explanations described why models behaved as they did from a single row. Claims are now checked against the ledger first, and hypotheses are labelled as hypotheses.

Same task for every system

JailbreakBench goals were used as jailbreaks, PII questions were broader than Bedrock's entity types, and unscored relevance leaked into grounding. Each suite now declares exactly which questions decide the score.

Clean splits

Pilot rows sat in the test split and related conversations crossed tune and test. Splits are now grouped, examined rows are excluded, and sampling is frozen.

Provable history

Results were moved between dataset versions by row id alone. They now move only when the row's full content is identical, recovered from git.

Before the held-out run

  • Human review of the authored cases: topic requests, prompt-attack controls and PII-free controls, about 70 rows.
  • Fill the named coverage gaps: masking scored on spans, relevance labels for grounding, indirect prompt injection from LLMail-Inject, a published topic source such as BARRED.
  • Pick each system's threshold on tuning rows for a stated false-positive budget, then report recall at that budget with intervals.
  • Freeze the evaluation contract and the held-out samples, with hashes recorded before any call.
  • Run the held-out comparison once, publish the dataset to Hugging Face, and build the results section on raxit.ai.
