Guardrail Benchmark for Decision Models

Plan for approval · 22 September 2026, revised same day after JevBench and Kev · raxIT Labs research project

Decision models (Jev and the open-weight Jev-class models behind it: Kev, OpenJev, djev, Winnow) all speak one contract: state and typed questions in, probabilities out. JevBench already ranks 52 of them on general decisions. Nobody has asked the question a buyer of guardrails asks: on the guardrail surface, with the same rows, how do they compare to the managed services they would replace, and to each other, on accuracy, calibration, policy adaptation, robustness to how the question is phrased, bias, latency, and cost. That is this benchmark.

What this benchmark is: the guardrail-domain companion to JevBench. Same class of subject, one contract for all of them, a different and harder set of questions. Subjects are decision models: Jev 1.13.0 and the top open-weight Jev-class models by JevBench rank. Baselines are what a buyer would otherwise use: Amazon Bedrock Guardrails, Google Model Armor, Azure AI Content Safety, OpenAI omni-moderation, one general LLM used as a classifier, and a regex floor. Not subjects: Llama Guard and the fixed-taxonomy guard models. One of them may appear as an anchor row so T1 to T3 can be checked against published numbers, clearly labelled as an anchor.

2. The benchmark, as a mechanism

Every system under test receives the same unified record and returns the same shape: a probability or score per task label. The harness never asks a system to explain itself. Decisions are made in the harness at thresholds fixed on a tuning split, so a vendor's default threshold and a fair threshold are both reported.

Decision-model metrics, on top of the guardrail metrics

Because every subject takes the same questions, we can measure things a fixed-taxonomy system cannot even be asked. These are the metrics that make it a decision-model benchmark rather than a guard-model benchmark with extra rows.

MetricHow it is measuredWhy it matters
Calibration (ECE, Brier)Reliability diagram per task on test, after tuning on tuneThe whole premise of "calibrated decisions"; Kev's own card reports Brier, so the field expects it
Fan-out invarianceSame row, same question, asked alone and inside a 15-question question set; report mean absolute driftVendors claim questions are independent; buyers pack question sets to save cost
Option-order sensitivityChoice questions with options shuffled across 5 seeds; report variance of the argmax and of probabilitiesJevBench observed it, nobody quantified it; small models are the suspects
Rephrase robustnessThree human paraphrases of each question set question; agreement across phrasingsA decision model is "as good as the question"; this measures how much
Criteria sensitivitySame question with and without criteria text, with negative carve-outs on and offTests the community's folk wisdom about carve-outs with numbers
Counterfactual biasT1 and T7 rows with names, dialects, or group markers swapped; report score deltas by groupSimon Willison's black-box critique, turned into a measurement
Policy-shift deltaT8: accuracy before and after a policy edit, no retraining, no new examplesThe one capability no fixed-taxonomy system has
Cost and latency$/1M evaluations from measured tokens and list price; p50 and p95 at concurrency 1 and 16, hosted and self-hosted both measured, never assumedJevBench adjusts self-hosted latency by a formula; we measure it

One taxonomy

Every source has its own categories. We map all of them onto the MLCommons AILuminate hazard taxonomy (12 hazards), plus three non-hazard labels the guardrail surface needs: injection, pii, unsafe_action. The mapping table is a versioned file and a design decision, not an afterthought. Where a vendor's category has no clean mapping (Bedrock's "Misconduct" spans four hazards), the mapping is many-to-one and reported per hazard.

3. Building the dataset

Target size

About 30k rows: 25k test, 5k tune. Roughly 12k on T1 to T3, 6k on T4 and T5, 4k on T6, 2k on T7, and 1k paired rows on T8. Enough for per-category confidence intervals, small enough to run every system for under a few hundred dollars.

Labels

Human labels only. Where a source used LLM labels (some WildGuardMix and BeaverTails slices), that is recorded in the datasheet and those rows are excluded from the headline, included in an appendix. This answers the one public critique of Jev's own numbers before it is raised.

Licences

Aegis CC-BY-4.0, ToxicChat CC-BY-NC, BeaverTails CC-BY-NC, WildGuard ODC-BY with gating, XSTest CC-BY, JBB MIT, pii-300k open. Non-commercial rows are fine for a research benchmark and flagged for anyone reusing the set commercially.

Language

English in v1. A small multilingual slice from Aegis (German, Spanish, Chinese) is held as a sanity check and reported separately, since Jev is English-first and Nemotron and Bedrock Standard tier claim broad coverage.

All subjects receive the identical question set per task. The question set text, criteria, and carve-outs are published verbatim and frozen before the full run. Baselines run at their documented defaults and, where they return a score, also at a threshold tuned on our tune split at 5% false-positive rate. Both numbers are published.

5. Harness

Stack

Python with uv, since every guard model and most SDKs are Python-first. pandas or polars for analysis, vLLM for open models, one adapter module per system, one Zod-equivalent (pydantic) schema for records and scores. The TypeScript question set from this repo ports to the Jev adapter in an afternoon.

Fairness rules, fixed before any run

Same rows for every system. No system sees test labels. Thresholds from tune only. Category definitions given to LLM classifiers and Jev are the AILuminate text, verbatim, the same for both. Latency measured one request at a time from one region, then again at concurrency 16. Cost from list prices on the run date.

Pre-registration

Tasks, metrics, thresholds policy, the taxonomy mapping, and the go/no-go for publishing are committed to the repo before the first full run. Changes after that are logged as amendments.

Reproducibility

Dataset pinned by sha256 and published on Hugging Face. Open-model runs reproducible on one A100 or H100. Managed-service runs reproducible with credentials; their receipts are published so the numbers survive a vendor changing the model.

6. What we expect to learn, stated as hypotheses

  • H1. On T1 to T3, Jev and the best open decision models land within a few F1 points of the managed services and the anchor guard model. Decision models do not win on plain content safety, and the benchmark should say so plainly.
  • H2. Calibration is where the class earns its name: ECE under 0.1 after tuning for Jev and the larger open models, worse for the sub-1B models, and much worse for LLM self-reported confidence and vendor severity buckets.
  • H3. The open Jev-class models trail Jev by a small, size-dependent margin on accuracy but fail differently: order sensitivity and fan-out drift grow sharply below 4B. This is the finding a self-hosting buyer needs and nobody has published.
  • H4. On T5, T7, and T8, managed services mostly cannot participate, and decision models beat the LLM classifier on cost by two orders of magnitude at similar accuracy. T8 policy-shift delta is small for decision models and undefined for the services.
  • H5. Counterfactual bias is measurable and non-zero for every subject; the question is whether it is larger for decision models than for the LLM classifier. We do not have a prior, which is the point of measuring.
  • H6. Rephrase and criteria sensitivity are large enough that a published question set is part of the result: two teams with different wording would rank the same models differently. If true, the benchmark's question set becomes a shared asset.

If H2 and H4 fail, the honest conclusion is that "decision model" is a cost story, not a capability story. Pre-registration commits us to publishing that.

8. Risks

  • Contamination. Guard models trained on the public sets will look better than they are. Mitigation: the contamination flag per row, a "clean" subset of crafted and post-training-cutoff rows, and reporting both.
  • Taxonomy mapping disputes. A vendor will argue their category was mapped unfairly. Mitigation: publish the map, offer a two-week notice period, accept mapping PRs with rerun.
  • Terms of service. Some managed services forbid benchmarking in their terms. Mitigation: read the terms before signing up, and where publishing is barred, run privately and report "not publishable under vendor terms" as a row.
  • Vendor drift. Bedrock updates its classifiers silently; Jev aliases move. Mitigation: pinned versions where possible, run dates on every number, receipts published.
  • Licence limits on redistribution. CC-BY-NC and gated sets. Mitigation: publish the record ids and mapping, not the text, for restricted sources, with a script that rebuilds the set from the originals.
  • Subject selection. Picking which open models to include is where bias creeps in. Mitigation: the rule is "Jev plus the top N on JevBench at the freeze date plus any model that mirrors the System One API and asks to be included", written down before the run.
  • Overlap with JevBench. Benchmark Heaven may extend into guardrail tasks. Mitigation: talk to them before week 5; offer our task set as a JevBench track if they prefer, and keep our harness Apache-2 either way.
  • Jev conflict of interest. We are also building on Jev. Mitigation: pre-registration, the Jev question set published verbatim, and an explicit prior (H1) that it will not win on content safety.

9. Decisions to make before week 1

  1. Subject rule: Jev plus the top N open Jev-class models on JevBench at freeze. N = 8 proposed. Include GPT-5.6 Luna as a decision model, yes or no.
  2. Baselines and credentials: Bedrock, Model Armor, Azure, OpenAI moderation; who funds the AWS, GCP, and Azure accounts.
  3. Scope of v1: all eight tasks and all eight decision-model metrics, or T1 to T4 plus T8 with calibration and cost first, robustness and bias probes in a second release.
  4. Whether to include the counterfactual bias probe in v1. It is the most likely to draw attention and the most likely to be disputed.
  5. Relationship with Benchmark Heaven: independent, or offer the guardrail tasks as a JevBench track.
  6. GPU: rented H100 hours or a local box.
  7. Publishing: Hugging Face dataset plus a raxIT Labs leaderboard; venue submission or not.
